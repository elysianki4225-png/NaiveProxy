# 加速模块与性能调优

> 本项目的「加速模块」是**自己实现的一段 Shell 逻辑**（就在 `naiveproxy-install.sh` 里，不下载、
> 不执行任何第三方脚本、不编译内核模块），通过 **Linux 内核网络参数 + 服务端连接复用参数** 来提升
> NaiveProxy（HTTP/2、HTTP/3 上的长连接隧道）在跨境高延迟、有丢包线路上的吞吐，并降低排队延迟。
>
> 安装时**默认自动启用**（档位 `standard`），不需要你做任何选择；装完就用，想关就一句命令。

---

## 1. 为什么 NaiveProxy 需要它

NaiveProxy 的特点是「**长得像正常网站流量**」，代价是：

| 特征 | 对性能的影响 |
| --- | --- |
| 隧道跑在 TLS + HTTP/2（或 HTTP/3）之上 | 单条连接承载全部流量，天生吃「拥塞控制 + 缓冲」 |
| 跨境链路 RTT 高、偶发丢包 | Linux 默认 `cubic` 一旦丢包就大幅降速，长肥管道跑不满 |
| 流量经过 padding / 多路复用 | 对 **MTU 黑洞、缓冲不足、空闲后重新慢启动** 特别敏感 |
| 服务端与客户端都是长连接 | 空闲连接被回收、keepalive 太慢都会造成抖动 |
| HTTP/3 走 UDP（QUIC） | 受 `rmem_max/wmem_max`、`udp_*_min`、网卡队列影响明显 |

所以本模块的调优方向是：**提高单流吞吐（BBR + 大缓冲）、降低延迟（fq + notsent_lowat）、
减少连接建立与重建成本（TFO、tw_reuse、keepalive、连接复用）**。

---

## 2. 安装时自动做了什么

安装脚本在第 6 步会自动执行 `accel_apply`（默认档位 `standard`），它做四件事：

1. **写参数文件** `/etc/sysctl.d/99-naiveproxy-accel.conf`（纯文本，可读可删，注释里写明每一项的作用）
2. **立即生效**：`modprobe tcp_bbr` / `sch_fq` + `sysctl -p /etc/sysctl.d/99-naiveproxy-accel.conf`
3. **逐项校验**：把每一项读回来对比，报告「N 项已生效 / M 项未生效」，不匹配会明确提示
4. **调整 Caddyfile**：`forward_proxy` 的 `max_idle_conns` / `max_idle_conns_per_host` 随档位放大

> 所有参数都是**上限或开关**，不预分配内存；参数文件删掉、重启后即恢复系统默认（见 §6）。

---

## 3. 三个档位

| 档位 | 适用场景 | 说明 |
| --- | --- | --- |
| `off` | 你有自己的调优方案 / 在受限容器里 | 不写参数文件；若之前启用过，会删除文件并恢复原拥塞控制与排队规则 |
| **`standard`（默认）** | 绝大多数 VPS（≥1GB 内存） | BBR + fq + 缓冲上限 16–32MB + TFO + 连接复用 256/16 |
| `aggressive` | 内存 ≥1.5GB、追求极限吞吐 | 队列更大、缓冲上限翻倍到 64MB、连接复用 512/32 |

安装时自动按内存选择**缓冲上限**（避免小内存机器被吃光）：

| 本机内存 | `rmem_max` / `wmem_max` |
| --- | --- |
| < 512 MB | 8 MB |
| 512 MB – 1 GB | 16 MB |
| ≥ 1 GB | 32 MB |
| ≥ 1.5 GB 且档位 `aggressive` | 64 MB |

## 4. 完整参数表（档位：standard / aggressive）

| 参数 | standard | aggressive | 为什么 |
| --- | --- | --- | --- |
| `net.ipv4.tcp_congestion_control` | `bbr` | `bbr` | 丢包链路上比 cubic 吞吐高得多，且不靠丢包判断拥塞 |
| `net.core.default_qdisc` | `fq` | `fq` | BBR 需要 fq 排队，避免 bufferbloat 导致延迟飙升 |
| `net.ipv4.tcp_notsent_lowat` | 128 KB | 128 KB | 不让内核「攒够数据再发」，交互与首包更快 |
| `net.ipv4.tcp_slow_start_after_idle` | 0 | 0 | 空闲后不重新慢启动：长连接隧道不被反复降速 |
| `net.ipv4.tcp_fastopen` | 3 | 3 | 客户端+服务端都开启 TFO，减少一次往返 |
| `net.ipv4.tcp_mtu_probing` | 1 | 1 | 自动探测 MTU，避免隧道/PPPoE 环境的 MTU 黑洞吞掉大包 |
| `net.ipv4.tcp_tw_reuse` | 1 | 1 | 复用 TIME_WAIT 连接，加快重连（对代理这种短连接多发的场景有用） |
| `net.ipv4.tcp_fin_timeout` | 15 | 15 | 缩短 FIN 等待，尽快回收端口 |
| `net.ipv4.ip_local_port_range` | 10240–65535 | 同左 | 扩大可用临时端口，避免高并发时端口耗尽 |
| `net.ipv4.tcp_keepalive_time/intvl/probes` | 60 / 15 / 4 | 同左 | 更快发现死连接并重建，减少「假死」 |
| `net.ipv4.tcp_max_syn_backlog` | 8192 | 32768 | 半连接队列，抗 SYN 突发 |
| `net.core.somaxconn` | 8192 | 32768 | 全连接队列，抗瞬时高并发 |
| `net.core.netdev_max_backlog` | 8192 | 32768 | 网卡收包队列，避免突发丢包 |
| `net.core.optmem_max` | 256 KB | 256 KB | 每 socket 辅助缓冲上限（UDP 场景同样受益） |
| `net.core.rmem_max` / `wmem_max` | 见 §3 内存表 | 翻倍 | socket 收发缓冲上限：高 BDP 链路不再被缓冲卡死；**quic-go 也按这个值设置 UDP 缓冲** |
| `net.ipv4.tcp_rmem` / `tcp_wmem` | `4096 <默认> <上限>` | 中值抬高到 1 MB | 自动调优的上下限，让内核敢放开发送窗口 |
| `net.ipv4.udp_rmem_min` / `udp_wmem_min` | 16 KB | 16 KB | QUIC 的 UDP socket 最小缓冲，提高 HTTP/3 吞吐 |
| `net.ipv4.tcp_max_tw_buckets` | 默认 | 131072 | 高并发下 TIME_WAIT 表更大 |

**应用层（写进 Caddyfile）**：

| 项 | off | standard | aggressive |
| --- | --- | --- | --- |
| `max_idle_conns` | 128 | **256** | 512 |
| `max_idle_conns_per_host` | 8 | **16** | 32 |

> 协议侧：脚本默认同时开启 HTTP/2 与 HTTP/3；预编译二进制自带
> `caddy-sing-quic-bbrv1.patch`，HTTP/3 的 BBR 带 v1 特性，配合本模块的 fq/缓冲设置效果更好。

## 5. 使用方法

```bash
# 查看当前档位、拥塞控制、缓冲上限、连接复用参数、本机内存
sudo bash naiveproxy-install.sh accel

# 切换档位（立即生效，无需重启 Caddy，也不需要重启系统）
sudo bash naiveproxy-install.sh accel apply --profile aggressive
sudo bash naiveproxy-install.sh accel apply --profile standard

# 关闭：删除参数文件，并把拥塞控制/排队规则恢复成安装前的值
sudo bash naiveproxy-install.sh accel off

# 安装时直接指定（默认就是 standard，一般不用写）
sudo bash naiveproxy-install.sh install --accel aggressive
sudo bash naiveproxy-install.sh install --accel off        # 完全不改内核参数
```

管理面板（`sudo bash naiveproxy-install.sh menu`）里的 **13) 加速模块** 也是同一套功能。

> 旧参数 `--bbr auto|yes|no` 仍可用（`yes/auto` → `--accel standard`，`no` → `--accel off`），
> 但推荐使用语义更清楚的 `--accel`。

---

## 6. 关闭与回滚

- `accel off` 会：删除 `/etc/sysctl.d/99-naiveproxy-accel.conf`，把 `tcp_congestion_control`
  和 `default_qdisc` 恢复成**安装前记录的值**（记录在 `/etc/caddy/naiveproxy/site.env` 的
  `ACCEL_PREV_CC` / `ACCEL_PREV_QDISC`），其它参数在下次重启后自然回到默认。
- 完全卸载（`uninstall`）时会自动执行同样的清理。
- 手动回滚：`sudo rm /etc/sysctl.d/99-naiveproxy-accel.conf && sudo sysctl -w net.ipv4.tcp_congestion_control=cubic`

## 7. 常见问题

**Q1：显示「N 项未生效」怎么办？**
常见于受限容器（LXC/OpenVZ/部分 KVM 面板）、或宿主机不允许改这些参数。脚本仍会保留参数文件，
系统重启后由 `systemd-sysctl` 再尝试一次；如果长期不生效，说明该环境不允许，
可以把档位设为 `off`（`accel off`），避免误导。

**Q2：会不会把内存吃光？**
不会。`rmem_max/wmem_max/tcp_rmem` 都是**上限**，只有真实流量很大时才会用到；
并且脚本按 §3 的内存表自动收缩，`aggressive` 档在内存 < 1.5 GB 时也不会把缓冲翻倍。

**Q3：和网上那些「一键加速脚本」有什么区别？**
参数就在仓库里，**没有 curl 外链脚本、没有安装第三方内核模块**，每一项都能看到原因（§4），
可随时 `accel off` 还原。你也能直接改这个文件后 `sysctl -p`。

**Q4：为什么不装 TCP Brutal 之类的内核模块？**
TCP Brutal 需要 DKMS 编译内核模块（Linux 5.10+），而且它的限速规则**按「目的地址」配置、重启后失效**，
需要针对每个客户端 IP 手动 `brutalctl add`；作为「一键装上就不用管」的默认方案并不合适。
如果你确实想用，可以自行安装它并按官方文档配置，本模块的 BBR/fq/缓冲设置与它不冲突（可共存）。

**Q5：HTTP/3 需要额外调优吗？**
只需要 `rmem_max/wmem_max` 与 `udp_*_min`（本模块已包含）以及放行 UDP 端口。
如果所在网络对 UDP 有 QoS/限速，用 `--http3 h2only` 只走 HTTP/2 更稳。

**Q6：怎么验证真的变快了？**
两侧都要看：服务端 `sysctl net.ipv4.tcp_congestion_control`、`ss -ti` 看 `bbr` 与 `cwnd`；
客户端用 `curl -o /dev/null -w '%{speed_download}\n'` 或 iperf3 对比开启前后。
注意：**协议开销、线路质量、对端限速**往往比内核参数影响更大，本模块解决的是「本该更快却被内核设置卡住」的问题。
